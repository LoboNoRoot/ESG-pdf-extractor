# PDF 指标提取流程通俗说明

这份文档用于向非计算机背景的老师解释：我们的项目是怎样从 ESG 报告 PDF 中提取指标的，以及 Python、RAG、LLM、embedding、MinerU 分别在流程中承担什么作用。

## 一句话概括

我们的系统不是简单地把整份 PDF 丢给大模型，也不是只靠 Python 规则硬提取。

更准确地说，它是一个“先找证据，再让大模型基于证据提取指标”的系统。

可以把它理解成一个有分工的团队：

- Python 像项目助理，负责打开 PDF、整理材料、切分文本、筛选重点页面、查找相关证据。
- MinerU 像版面解析专家，负责处理复杂表格、扫描页、图文混排等普通文本提取不好的页面。
- RAG 像资料检索员，负责从大量报告内容里找出和某个指标最相关的几段证据。
- LLM 像阅读理解能力很强的研究助理，负责基于证据判断指标是否披露，并提取数值、单位、年份和证据句。
- embedding 像语义搜索工具，帮助系统找到“意思相近但字面不完全一样”的证据。

## 先澄清几个容易混淆的概念

### 1. RAG 不是 LLM

RAG 不是大模型本身，而是一套使用大模型的方法。

RAG 的完整意思可以理解为：先检索资料，再让大模型回答或抽取。

在我们的项目里，RAG 的流程是：

1. 先从 PDF 中解析出文本和表格相关内容。
2. 把这些内容切成很多小段，叫做 chunks。
3. 针对每一个 ESG 指标，从 chunks 里找最相关的证据。
4. 把“指标定义 + 相关证据”交给 LLM。
5. LLM 基于证据输出结构化结果。

所以，LLM 是 RAG 流程的最后一步，不是 RAG 的全部。

### 2. 我们不是把所有证据一次性都给 LLM

如果把一整份 ESG 报告全部交给 LLM，会有几个问题：

- 报告太长，token 成本高。
- 页数多，模型容易遗漏重要表格。
- 证据太杂，模型容易混淆年份、单位和指标。
- 结果不容易追溯到具体页码和原文。

所以我们的做法是：

先把整份报告变成可检索的证据库。真正抽取某个指标时，只从证据库中取出和这个指标最相关的几段内容，再交给 LLM。

比如要抽“温室气体排放总量”，系统不会把整份报告给 LLM，而是先检索出包含“温室气体”“碳排放”“二氧化碳当量”“排放总量”等相关内容的几个文本块，再让 LLM 判断哪个数值才是目标指标。

### 3. 指标提取不是纯 Python，也不是纯 LLM

Python 主要负责“整理和检索”。

LLM 主要负责“理解和判断”。

Python 负责：

- 读取 PDF。
- 扫描页面。
- 判断哪些页面像指标表、绩效表、数据表。
- 调用 MinerU。
- 把文本切成小块。
- 为每个指标检索相关证据。
- 组织 prompt。
- 校验 LLM 输出的年份、单位、证据和置信度。

LLM 负责：

- 判断某个指标是否在证据中披露。
- 从证据中提取数值。
- 判断单位是什么。
- 判断年份是否对应目标年份。
- 提取支持结论的证据句。
- 输出固定格式的 JSON 结果。

所以我们的系统是“程序检索 + 大模型理解”的混合方案。

## 为什么不能只用 Python 规则提取

ESG 报告的写法非常不统一。

同一个指标可能有很多表达方式。例如“温室气体排放总量”可能写成：

- 温室气体排放总量
- 碳排放总量
- GHG emissions
- 二氧化碳当量排放
- 范围一及范围二排放合计

如果只靠 Python 写规则，就要提前穷举所有可能写法。现实中不同公司、不同行业、不同年份报告表达差异很大，规则很难覆盖。

另外 ESG 报告里常见多年份表格，例如：

| 指标 | 2022 | 2023 | 2024 | 单位 |
| --- | --- | --- | --- | --- |
| 综合能耗 | 100 | 120 | 135 | 吨标准煤 |

系统必须知道目标年份是 2024，并取 135，而不是取 100 或 120。这个过程既需要文本定位，也需要语义理解和表格对齐。

因此我们让 Python 先把相关证据找出来，再让 LLM 做最后的语义判断。

## 为什么不能只用 LLM 直接读整份 PDF

直接让 LLM 读整份 PDF 看起来简单，但不适合批量、可追溯、可评估的指标抽取任务。

主要原因有四个。

第一，成本高。

一份 ESG 报告可能几十页到上百页。如果每份报告都完整输入 LLM，token 成本很高。

第二，容易遗漏。

ESG 指标经常藏在表格、附录、指标索引或图文混排页面里。直接让模型读整份文档，模型不一定稳定找到所有字段。

第三，容易混淆。

报告中可能同时出现 2022、2023、2024 多年数据，也可能出现集团口径、子公司口径、范围一、范围二等不同统计口径。直接全量输入时，模型容易拿错数字。

第四，不利于审查。

老师或人工复核人员需要知道：这个结果来自哪一页、哪一句、哪个表格行。我们的系统会保存 `source_page`、`source_chunk_id` 和 `evidence`，方便追溯。

## 项目整体流程

下面用比较通俗的方式讲一遍完整流程。

## 第一步：判断这是不是适合处理的 ESG 报告

系统会先看上传的 PDF 是否像完整 ESG 报告。

如果是鉴证声明、审验报告、摘要、传统社会责任报告，或者标题层面缺少 ESG 披露框架信号，系统可能会跳过。

这样做是为了避免把不适合的文件送进后续流程，浪费解析和模型调用成本。

## 第二步：用 PyMuPDF 快速扫描整份 PDF

PyMuPDF 是一个 Python PDF 处理工具。

它的作用类似于先快速翻一遍报告，看看每一页大概是什么内容。

系统会逐页统计：

- 这一页有多少文字。
- 这一页有多少数字。
- 是否出现 2024、2023 等年份。
- 是否出现 ESG 关键词，如环境、社会、治理、碳、员工、安全、董事会等。
- 是否出现表格关键词，如关键绩效、指标表、ESG 数据、单位等。
- 是否像表格页面。
- 是否是扫描页或低文本页面。

然后系统会给每一页打一个分数，叫 `mineru_score`。

分数高的页面，通常更可能包含重要指标表或复杂表格。

## 第三步：决定哪些页面需要 MinerU 深度解析

MinerU 是一个更强的文档解析工具，适合处理复杂版面和表格。

但 MinerU 解析比普通文本提取更重，所以我们不对所有页面都调用 MinerU。

我们的策略是“选择性调用 MinerU”。

也就是说：

- 普通正文页，用 PyMuPDF 就够了。
- 关键绩效表、环境数据表、员工数据表、治理指标表等重点页，调用 MinerU。
- 扫描页、低文本层页、图文混排页，作为后续视觉兜底候选。

这样可以兼顾准确率和处理成本。

## 第四步：把 PDF 内容变成证据块

系统会把报告文本切成一段一段的小块，这些小块叫 chunks。

每个 chunk 都会记录：

- 这段文字来自哪里。
- 是 PyMuPDF 解析的，还是 MinerU 解析的。
- 来自第几页。
- 文本内容是什么。

这样后面抽取结果就可以追溯。

比如一个 chunk 可能是：

```text
chunk_id: pymupdf_layout_p35_1
source: pymupdf_layout
page: 35
text: 2024 年温室气体排放总量为 12000 吨二氧化碳当量...
```

## 第五步：针对每个指标检索证据

我们项目有一个 A 股 ESG 指标体系，目前是 60 个字段。

每个字段不仅有一个字段名，还会配置：

- 中文名称。
- 指标类别，属于 E、S 还是 G。
- 指标类型，是定量、定性还是混合。
- 别名。
- 搜索词。
- 预期单位。
- 领域知识。

比如“用水总量”这个字段，可能会有别名和关键词：

- 总用水量
- 取水量
- 水资源消耗
- 立方米
- 吨

系统会根据这些信息，在所有 chunks 中检索最相关的证据。

默认情况下，系统使用 BM25 这类关键词检索方法。可以简单理解为：哪个文本块和这个指标的关键词更匹配，哪个文本块就排得更靠前。

## 第六步：embedding 在哪里发挥作用

embedding 可以理解为“把文字变成一串数字向量，用来表示语义”。

如果两段文字意思接近，即使字面不完全一样，它们的向量也会更接近。

例如：

- “温室气体排放总量”
- “碳排放总量”
- “GHG emissions”
- “二氧化碳当量排放”

这些词字面不同，但语义相关。embedding 可以帮助系统把它们联系起来。

在当前满血版配置中，系统默认使用 hybrid 混合检索，并启用 embedding 向量召回。

hybrid 检索大概是：

1. 用关键词方法找一批候选证据。
2. 用 embedding 语义相似度再找一批候选证据。
3. 把两批结果融合排序。
4. 选出最相关的几个证据块交给 LLM。

这样可以兼顾关键词精确匹配和语义相似匹配。

真实 embedding 需要调用外部模型接口，会产生一定成本；如果接口不可用，系统会自动回退到本地向量兜底。普通关键词检索仍可作为对照实验或低成本模式使用。

## 第七步：LLM 基于证据进行结构化抽取

当系统已经为某个指标找到相关证据后，会把这些内容交给 LLM。

LLM 看到的不是整份报告，而是类似下面这样的信息：

```text
请抽取字段：温室气体排放总量
指标类型：定量
预期单位：吨二氧化碳当量、tCO2e
目标年份：2024

相关证据：
1. 第 35 页：2024 年温室气体排放总量为 12000 吨二氧化碳当量。
2. 第 36 页：范围一排放 3000 吨，范围二排放 9000 吨。

请输出 JSON。
```

然后 LLM 输出结构化结果：

```json
{
  "field_key": "ghg_emissions_total",
  "matched": true,
  "value": "12000",
  "unit": "吨二氧化碳当量",
  "year": "2024",
  "evidence": "2024 年温室气体排放总量为 12000 吨二氧化碳当量",
  "source_page": 35,
  "confidence": 0.92
}
```

这就是 LLM 在项目里的核心作用：基于证据做阅读理解，并按照固定格式输出结果。

## 第八步：对 LLM 结果做质量检查

LLM 输出之后，系统不会完全不检查。

Python 代码还会做后处理，包括：

- 检查年份是否是目标年份。
- 检查单位是否合理。
- 检查证据中是否真的包含数值。
- 检查证据中是否出现目标年份。
- 检查置信度是否过低。
- 检查证据是否太弱。
- 对多年份表格进行目标年份对齐。

例如目标年份是 2024，但 LLM 输出了 2023，系统会标记年份异常。

如果证据里出现多个数字，但没有出现 2024，系统会降低置信度，并提示需要人工复核。

## 系统最终输出什么

系统最终会生成几类文件。

`page_scan.json`

记录每页的扫描结果，比如关键词、数字数量、是否需要 MinerU。

`parse_plan.json`

记录哪些页面用 PyMuPDF，哪些页面用 MinerU。

`rag_chunks.json`

记录从 PDF 解析出来的所有证据块。

`field_contexts.json`

记录每个指标对应召回到哪些证据。

`extraction_results.json`

记录最终 60 个指标的抽取结果。

`extraction_results.csv`

把结果导出成表格，方便人工复核和展示。

`extraction_summary.json`

记录整体抽取情况，比如抽中了多少字段、调用了多少次 LLM、有多少质量警告。

## 技术栈说明

### Python

Python 是整个后端流程的主语言。

它负责 PDF 处理、流程调度、证据检索、模型调用、结果保存和质量检查。

### PyMuPDF

用于快速读取 PDF 文本，逐页扫描内容。

它适合做低成本的全文快速扫描。

### MinerU

用于复杂 PDF 页面解析。

它适合处理表格、复杂版面、扫描页和图文混排内容。

### RAG

RAG 是“先检索证据，再让大模型抽取”的工作流程。

它不是单独某一个模型，而是一整套证据组织方法。

### BM25

BM25 是一种关键词检索方法。

它负责根据字段名、别名、搜索词和单位，从 chunks 中找相关文本。

### embedding

embedding 是语义向量检索方法。

它可以找到字面不一样但意思相近的证据。

例如“碳排放”和“温室气体排放”可能被认为语义相关。

### LLM

LLM 是大语言模型。

在我们的项目里，它负责基于检索到的证据做最终指标抽取。

它不会直接凭空生成，而是被要求只基于证据输出。

### FastAPI

FastAPI 用来提供后端接口。

例如上传 PDF、创建任务、查询任务、查看结果、导出 CSV。

### 前端页面

前端用于展示抽取结果、证据和人工复核状态。

老师或人工复核人员可以看到某个指标的值、单位、年份、证据和页码。

## 一个完整例子

假设我们要从一份 ESG 报告中抽取“用水总量”。

系统会这样做：

1. PyMuPDF 扫描整份报告。
2. 发现第 40 页有很多数字、年份、单位，并出现“环境绩效”“用水量”等词。
3. 系统判断第 40 页可能是重点数据页。
4. 如果需要，就调用 MinerU 深度解析第 40 页。
5. 系统把报告内容切成 chunks。
6. 对“用水总量”这个指标，系统检索包含“用水总量”“取水量”“水资源消耗”“立方米”等词的证据块。
7. 系统把最相关的几个证据块交给 LLM。
8. LLM 判断 2024 年用水总量是多少，单位是什么，证据是哪一句。
9. 系统检查年份、单位和证据是否合理。
10. 最后输出 JSON 和 CSV。

## 老师可能追问的问题

### 问：你们到底有没有用大模型？

有。

大模型主要用于最后的指标抽取，也可以用于判断某些灰区页面是否需要 MinerU 深度解析。

但我们不是把整份 PDF 直接丢给大模型，而是先检索证据，再让大模型基于证据抽取。

### 问：Python 代码是不是已经把指标提取完了？

不是。

Python 代码主要做 PDF 解析、证据切分、证据检索和结果校验。

真正的语义判断和结构化抽取由 LLM 完成。

### 问：RAG 和 LLM 是什么关系？

RAG 是流程，LLM 是流程中的一个组件。

RAG 先找证据，再把证据交给 LLM。

### 问：embedding 是不是一定会用？

不一定。

当前正式配置默认使用 BM25 + embedding 的混合检索。关键词检索可以作为对照实验或低成本备用模式。

### 问：为什么需要 MinerU？

因为 ESG 报告中有很多表格、复杂排版和扫描页。

普通 PDF 文本提取工具有时会漏掉表格结构或读乱顺序，MinerU 可以增强这些复杂页面的解析质量。

### 问：结果是否可以人工复核？

可以。

系统输出 CSV、JSON 和证据信息。每个字段都有证据文本、页码、置信度和质量警告，方便人工复核。

## 最适合汇报的一段总结

我们的 PDF 指标提取流程采用的是“选择性文档解析 + RAG 证据检索 + LLM 结构化抽取”的技术路线。

首先，系统用 PyMuPDF 快速扫描整份 ESG 报告，识别哪些页面可能包含关键指标表或复杂表格；然后，对重点页面调用 MinerU 进行深度解析，提升表格和图文混排页面的文本质量；接着，系统把 PyMuPDF 和 MinerU 得到的内容统一切成可检索的证据块；之后，针对每个 ESG 指标，从证据块中召回最相关的内容；最后，LLM 基于这些证据完成数值、单位、年份、证据句和置信度的结构化输出。

因此，我们的系统不是纯规则抽取，也不是纯大模型抽取，而是把传统程序的稳定性、检索系统的可追溯性和大模型的语义理解能力结合起来。
