\section{系统整体处理流程}

\subsection{处理逻辑介绍}

系统的输入是一份 ESG 报告 PDF，输出为字段级结构化结果、证据页码、人工复核状态、CSV 文件和指标图表。在实际处理时，程序不会把整份 PDF 直接输入给大模型，而是先扫描页面内容，找出与 ESG 指标相关的文本块，再把这些文本块作为候选证据交给大模型。这样既可以减少输入内容，也方便后续查看每个结果来自哪一页。

\manualfigure{system_overall_flow(3).pdf}{系统整体处理流程图}

系统主流程如下：

\begin{enumerate}
  \item 用户在服务器部署后的 Web 系统中上传 ESG 报告 PDF，或通过批量采集脚本准备报告文件。
  \item 后端先进行报告有效性判断，过滤鉴证声明、摘要、非完整 ESG 报告等异常输入。
  \item 使用 PyMuPDF 对 PDF 做页级快扫，提取文本长度、ESG 关键词、数值密度、表格线索和低文本页特征。
  \item 根据页级特征生成 MinerU 解析计划，选择最可能包含指标表或复杂版式的重点页面。
  \item 对重点页生成子 PDF，并调用 MinerU 进行深度解析，避免整份报告全量解析。
  \item 将 PyMuPDF 文本、PyMuPDF 视觉布局文本和 MinerU 文本统一切分为 RAG 文本块。
  \item 针对 60 个 ESG 字段分别检索证据，使用 BM25算法 和 embedding 向量召回，并通过 RRF 融合排序。
  \item 将字段定义和候选证据交给 OpenAI-compatible 大模型，输出结构化 JSON 结果。
  \item 对抽取结果进行目标年份对齐、单位校验、证据质量评分和复核优先级计算。
  \item 前端展示抽取结果和证据，用户可确认、驳回或编辑字段结果。
  \item 系统将最终结果保存到 PostgreSQL，并支持 CSV 导出和 ECharts 指标分析。
\end{enumerate}

\section{服务器部署技术详解}

\subsection{部署结构介绍}

系统以 Docker Compose 方式部署在服务器上。部署后主要包含两个容器：\texttt{api} 和 \texttt{postgres}。\texttt{api} 容器负责运行 FastAPI 后端、React 静态前端和 MinerU 解析环境；\texttt{postgres} 容器负责存储报告、任务、抽取结果、复核记录和指标分析数据。

\manualfigure{server_deployment_topology(3).pdf}{服务器部署拓扑图}

\begin{lstlisting}
用户浏览器
    |
    | HTTP:8000
    v
服务器 Docker Compose
    |-- api 容器
    |     |-- FastAPI 后端
    |     |-- React 静态前端
    |     |-- MinerU 解析环境
    |     |-- /app/data
    |     `-- /app/output
    `-- postgres 容器
          `-- PostgreSQL 16 数据库
\end{lstlisting}

\subsection{Dockerfile 构建流程}

Dockerfile 使用多阶段构建。

\begin{enumerate}
  \item 前端构建阶段使用 \texttt{node:22-slim}。该阶段先复制前端依赖文件，再执行 \texttt{npm ci} 和 \texttt{npm run build}，生成 React 静态文件。
  \item 后端运行阶段使用 \texttt{python:3.11-slim}，复制后端源码、配置文件、\texttt{requirements-mineru.txt} 和前端构建产物。
  \item 安装系统依赖 \texttt{libgl1}、\texttt{libglib2.0-0}，满足 OpenCV 和 MinerU 相关依赖。
  \item 从 PyTorch CPU index 单独安装 \texttt{torch} 和 \texttt{torchvision}。
  \item 安装 \texttt{requirements-mineru.txt} 中固定版本的 MinerU 运行依赖。
  \item 安装当前 Python 项目，最后通过 Uvicorn 启动 FastAPI。
\end{enumerate}

容器启动命令如下：

\begin{lstlisting}
uvicorn esg_selective_mineru.api:app --host 0.0.0.0 --port 8000
\end{lstlisting}

\subsection{MinerU 运行环境配置}

当前项目新增 \texttt{requirements-mineru.txt}，用于固定 MinerU 运行时依赖。该文件包含 \texttt{mineru==3.2.3} 以及解析、视觉、OCR、模型下载和文档处理相关依赖。由于 PyTorch 安装源和普通 PyPI 依赖源不同，Dockerfile 将 \texttt{torch} 和 \texttt{torchvision} 从 PyTorch CPU index 单独安装，再安装 MinerU 依赖清单。

该设计的作用包括：

\begin{itemize}
  \item 保证服务器容器内具备 MinerU 运行环境。
  \item 避免每次部署时依赖版本漂移。
  \item 降低 MinerU 与普通后端依赖混装造成的冲突。
  \item 让服务器部署时不依赖宿主机已有的 MinerU 环境。
\end{itemize}

\section{数据采集技术详解}

\subsection{巨潮资讯网采集逻辑介绍}

报告采集脚本为 \texttt{scripts/collect\_a\_share\_esg\_reports.py}，用于从巨潮资讯网（CNINFO）批量采集 A 股上市公司 ESG 相关公告 PDF，并生成报告清单。该脚本不依赖浏览器自动化工具，而是直接调用巨潮资讯公告检索接口，通过关键词、页码、时间范围和股票代码等参数检索公告，再下载公告对应的 PDF 文件。

\manualfigure{report_collection_flow.pdf}{报告采集流程图}

\subsubsection{采集目标与数据来源}

爬虫的数据来源为巨潮资讯网公告检索接口：

\begin{lstlisting}
http://www.cninfo.com.cn/new/hisAnnouncement/query
\end{lstlisting}

公告 PDF 的静态资源根地址为：

\begin{lstlisting}
http://static.cninfo.com.cn/
\end{lstlisting}

脚本通过公告检索接口获取公告元数据，再根据公告字段中的 \texttt{adjunctUrl} 拼接或识别 PDF 下载地址。采集对象主要包括上市公司发布的 ESG 报告、环境、社会和公司治理报告、社会责任报告和可持续发展报告等。

默认关键词包括：

\begin{itemize}
  \item ESG 报告；
  \item 环境、社会和公司治理报告；
  \item 社会责任报告；
  \item 可持续发展报告。
\end{itemize}

这些关键词覆盖了 A 股上市公司常见的 ESG 信息披露文件命名方式。用户也可以通过命令行参数重复传入 \texttt{--keyword}，扩展或替换默认检索关键词。

\subsubsection{检索请求构造}

爬虫使用 \texttt{urllib.request} 发送 POST 表单请求。检索请求的核心参数包括：

\begin{manualtable}{p{4cm}p{10cm}}
\toprule
\textbf{参数} & \textbf{说明} \\
\midrule
\endhead
\texttt{pageNum} & 当前检索页码。 \\
\texttt{pageSize} & 每页返回公告数量。 \\
\texttt{column} & 公告所属市场列，脚本中使用 \texttt{szse}。 \\
\texttt{tabName} & 检索范围，脚本中使用 \texttt{fulltext}。 \\
\texttt{searchkey} & 检索关键词，如 ESG 报告、可持续发展报告等。 \\
\texttt{stock} & 股票代码过滤条件，可为空。 \\
\texttt{seDate} & 公告时间范围，例如 \texttt{2021-01-01\textasciitilde 2024-12-31}。 \\
\texttt{sortName} & 排序字段，脚本中按公告时间排序。 \\
\texttt{sortType} & 排序方式，脚本中使用倒序。 \\
\texttt{isHLtitle} & 是否开启标题高亮。 \\
\bottomrule
\end{manualtable}

请求头中设置了 \texttt{User-Agent}、\texttt{Referer}、\texttt{Content-Type} 和 \texttt{Accept}，用于模拟普通网页请求并获取 JSON 格式响应。接口响应中的 \texttt{announcements} 字段即为公告列表。

\subsubsection{分页遍历与公告去重}

采集函数会按照“关键词—页码”的双层循环遍历公告列表。对于每个关键词，脚本从第 1 页开始请求，直到达到设定页数或当前页无结果为止。为了避免多个关键词命中同一公告，脚本使用 \texttt{seen} 集合进行去重。

去重键优先使用公告 PDF 的 \texttt{adjunctUrl}。如果该字段缺失，则使用证券代码、公告标题和公告时间构造备用键。只有 PDF 文件才会进入下载流程，非 PDF 附件会被跳过。

该策略可以避免以下问题：

\begin{itemize}
  \item 同一份 ESG 报告同时被多个关键词命中；
  \item 同一公告在多页结果中重复出现；
  \item 非 PDF 附件被误下载；
  \item 重复文件进入后续预处理和抽取流程。
\end{itemize}

\subsubsection{PDF 下载与安全命名}

公告下载函数 \texttt{\_download()} 通过流式读取方式保存 PDF 文件，每次读取 1 MB 数据块，避免一次性将完整文件加载到内存中。文件保存前会自动创建父目录。

文件命名时，脚本会对证券代码、证券简称和公告标题进行安全清洗。清洗逻辑包括：

\begin{itemize}
  \item 使用 \texttt{html.unescape()} 还原 HTML 实体；
  \item 去除公告标题中的 \texttt{<em>} 高亮标签；
  \item 将路径非法字符、空白字符替换为下划线；
  \item 限制标题长度，避免文件名过长。
\end{itemize}

最终文件名由报告编号和公告标题组成。报告编号包含证券代码、证券简称、公告年份和序号，例如：

\begin{lstlisting}
000001_平安银行_2024_001_2024年度ESG报告.pdf
\end{lstlisting}

这种命名方式便于后续从文件名中推断公司、年份和报告信息。

\subsubsection{限速控制与异常处理}

为了减少对目标网站的请求压力，脚本在分页请求和文件下载之间加入 \texttt{sleep} 间隔，默认间隔为 0.8 秒。用户可以通过 \texttt{--sleep} 参数调整请求间隔。

当 PDF 下载失败时，脚本不会中断整个采集任务，而是打印失败公告的证券代码、标题和错误信息，并继续采集下一条公告。这样可以保证批量采集任务具有一定容错能力。

\subsection{PDF 预处理}

\subsection{报告有效性判断}

报告过滤逻辑位于 \texttt{report\_filter.py}。系统在正式解析前先判断上传文件是否适合进入 ESG 指标抽取流程。该步骤可以避免鉴证声明、审验报告、摘要等非完整报告进入高成本 MinerU 和 LLM 链路。

过滤规则包括：

\begin{itemize}
  \item 标题层面缺少 ESG、环境社会治理、可持续发展等披露框架信号的传统社会责任报告会被跳过。
  \item 鉴证声明、审验报告、摘要等支持性文件会被跳过。
  \item 无法打开或无法解析的 PDF 会记录异常原因。
\end{itemize}

被跳过的报告不会进入 MinerU 和 LLM 抽取阶段，系统会输出 \texttt{skip\_report.json} 和 \texttt{run\_summary.json}。

\section{报告解析技术详解}

\subsection{PDF 页面扫描流程}

页级快扫由 \texttt{page\_scan.py} 完成。该模块使用 PyMuPDF 逐页读取 PDF 文本层，并计算页面特征。页级快扫的目标不是完整理解报告，而是快速判断哪些页面更可能包含 ESG 指标表、绩效表或复杂版式内容。

\begin{manualtable}{p{3.5cm}p{5cm}p{6cm}}
\toprule
\textbf{快扫特征} & \textbf{技术含义} & \textbf{用途} \\
\midrule
\endhead
文本长度 & 当前页可提取文本长度 & 判断文本层是否完整。 \\
ESG 关键词 & 环境、社会、治理、碳、员工、安全等关键词命中情况 & 判断页面主题相关性。 \\
数值数量 & 数字、百分比、计量单位等出现数量 & 判断是否可能包含定量指标。 \\
表格线索 & 指标项、单位、绩效表、连续数值等线索 & 判断是否可能包含 ESG 数据表。 \\
低文本页 & 文本层较少但页面可能包含图片或扫描内容 & 标记视觉解析候选页面。 \\
MinerU 分数 & 多种特征加权后的页面解析价值 & 判断页面是否进入 MinerU。 \\
\bottomrule
\end{manualtable}

\manualfigure{page_scan_feature_diagram.pdf}{页级快扫特征示意图}

\subsection{重点页面筛选方法}

解析计划由 \texttt{parse\_plan.py} 生成。该模块读取 \texttt{page\_scan.json}，根据页面得分、阈值和最大页数限制，选择需要进入 MinerU 的页面。

解析计划主要包含：

\begin{itemize}
  \item \texttt{page\_count}：报告总页数。
  \item \texttt{mineru\_pages}：进入 MinerU 的重点页面。
  \item \texttt{visual\_fallback\_pages}：后续可能需要视觉模型兜底的页面。
  \item \texttt{pages}：每页的解析策略和评分详情。
\end{itemize}

系统通过 \texttt{SELECTIVE\_MINERU\_MAX\_PAGES} 控制每份报告最多进入 MinerU 的页面数，避免对整份报告做高成本解析。

\subsection{重点页子 PDF 生成流程}

当前版本中，MinerU 调用前新增了重点页子 PDF 生成步骤。该逻辑位于 \texttt{mineru\_runner.py} 的 \texttt{\_create\_page\_subset\_pdf()}。系统会根据 \texttt{parse\_plan.json} 中的 \texttt{mineru\_pages}，从原 PDF 中抽取这些页面，生成一个只包含重点页的临时 PDF，再交给 MinerU 解析。

该机制的作用包括：

\begin{itemize}
  \item 减少 MinerU 输入页数，降低解析时间和资源占用。
  \item 避免 MinerU 对封面、目录、普通正文页等低价值页面重复解析。
  \item 保留选择性解析策略的一致性，使 \texttt{mineru\_jobs.json} 中可以记录实际解析页数。
  \item 便于测试和追踪 MinerU 实际处理了哪些页面。
\end{itemize}

\manualfigure{selective_mineru_subset_flow(1).pdf}{选择性 MinerU 子 PDF 解析流程图}

\subsection{MinerU 解析流程}

MinerU 调用逻辑位于 \texttt{run\_mineru()}。该函数接收 PDF 路径、输出目录、命令模板、超时时间和选中页列表。运行后，系统会记录以下信息：

\begin{itemize}
  \item 是否尝试调用 MinerU。
  \item MinerU 返回状态。
  \item 标准输出和错误输出尾部。
  \item 实际执行命令。
  \item 实际输入 PDF 路径。
  \item 选中的页面列表和页面数量。
\end{itemize}

这些信息写入 \texttt{mineru\_jobs.json}，用于排查解析失败、超时或页面选择异常。

\subsection{灰区页面复判方法}

灰区页面复判由 \texttt{mineru\_page\_judge.py} 完成。对于页面分数处于低阈值和高阈值之间的页面，系统可调用 LLM 判断是否值得进入 MinerU。该功能通过 \texttt{MINERU\_LLM\_REVIEW\_ENABLED} 控制是否启用，并通过 \texttt{MINERU\_LLM\_REVIEW\_MAX\_PAGES} 限制最大复判页数。

该设计用于避免“员工学历结构”被抽成“员工总数 8401 人”这类口径错误。结构型字段在 Prompt 中会被明确提示为分布结构；质量校验阶段也会清空不可靠的单一 \texttt{value} 和 \texttt{unit}，保留证据和摘要，交由前端复核。

\section{字段证据检索技术详解}

\subsection{文本块来源说明}

文本块构建逻辑位于 \texttt{chunks.py}。当前系统的 RAG chunks 来自三类文本：

\begin{enumerate}
  \item \textbf{PyMuPDF 视觉布局文本}：通过 \texttt{page.get\_text("words")} 提取词和坐标，再按页面视觉位置重排行列。
  \item \textbf{PyMuPDF 普通文本}：通过普通文本层提取，适合正文段落。
  \item \textbf{MinerU 文本}：读取 MinerU 输出的 Markdown 或文本文件，补充复杂表格和版式内容。
\end{enumerate}

\subsection{PyMuPDF 视觉顺序重排}

当前版本新增 \texttt{\_words\_to\_visual\_lines()}，用于将 PyMuPDF 提取的 words 按视觉位置排序。该函数先根据 y 坐标聚合为行，再按 x 坐标排列每行内的词，最后拼接为接近人眼阅读顺序的文本。

该机制主要解决 PDF 表格文本提取中的一个常见问题：普通文本提取可能打乱表格行列顺序，导致年份、单位和数值错位。视觉顺序文本可以更好地保留表格横向结构，为后续目标年份对齐提供基础。

\manualfigure{pymupdf_visual_layout_reorder(1).pdf}{PyMuPDF 视觉布局文本重排示意图}

\subsection{文本块切分方法}

系统将文本切分为适合检索和模型输入的小段，每个 chunk 保留来源信息。典型字段如下：

\begin{itemize}
  \item \texttt{chunk\_id}：文本块编号。
  \item \texttt{source}：文本来源，如 \texttt{pymupdf\_layout}、\texttt{pymupdf}、\texttt{mineru}。
  \item \texttt{page}：来源页码。
  \item \texttt{text}：文本内容。
\end{itemize}

\subsection{BM25算法 关键词召回}

BM25算法 召回由 \texttt{SimpleRetriever} 实现。系统会从字段定义中提取字段名、字段编码、主题词、别名、搜索词和期望单位，将其组合为查询文本，再计算每个 chunk 与查询文本的相关性。BM25算法 适合字段名称、单位和关键词直接出现的场景。

\subsection{Embedding 向量召回}

Embedding 向量召回由 \texttt{EmbeddingVectorRetriever} 实现。系统在 hybrid 模式下可调用 OpenAI-compatible Embedding API，将字段查询和文本块转换为向量，再通过 cosine similarity 计算语义相似度。

启用 embedding 的关键配置为：

\begin{lstlisting}
RETRIEVER_MODE=hybrid
RETRIEVER_VECTOR_BACKEND=embedding
EMBEDDING_MODEL=text-embedding-v4
\end{lstlisting}

Embedding 召回适合处理报告中表达方式不完全一致的情况。例如字段定义为“温室气体排放总量”，报告中可能写作“GHG emissions”“二氧化碳当量排放”或“范围一及范围二排放合计”。语义向量可以提高这类证据的召回概率。

\subsection{本地向量备用方案}

如果 embedding API key 缺失或调用失败，系统会自动回退到本地字符 n-gram TF-IDF 向量，并在结果中标记 \texttt{vector\_backend: local\_fallback}。本地向量用于异常兜底和离线测试，不作为服务器正式运行时的主要召回能力。

\subsection{RRF 融合排序}

\texttt{HybridRetriever} 会同时执行 BM25算法 和 embedding 向量召回，再使用 RRF 方法融合结果。RRF 可以避免单一召回方式带来的偏差：BM25算法 更重视关键词精确命中，embedding 更重视语义相似度，融合后优先保留两类方法都认为相关的证据。

在 RRF 融合后，系统还会执行字段级重排。字段级重排会根据字段名、别名、搜索词、必需语义词和期望单位计算 \texttt{field\_match\_score}，并对命中 \texttt{forbidden\_any} 的证据进行降权。该步骤用于解决相近指标之间的串扰，例如“总用水量”不应被“能源消耗总量”或“绿电”表格挤占，“供应商 ESG 或可持续评估”也不应仅因出现“供应商数量 1436 家”就被判定为已披露 ESG 评估数量。

除 BM25算法 和向量召回结果外，系统还会从全部 chunks 中补充字段精确候选池。只要文本块明确包含字段名、别名或搜索词，就会进入最终重排候选。该机制可以避免表格页在向量排名中靠后时被 \texttt{RAG\_TOP\_K} 截断，尤其适用于绩效表中字段密集、多个指标共享同一页的情况。当前默认每个字段最终送入 LLM 的证据块数量为 \texttt{RAG\_TOP\_K=8}。

\begin{manualtable}{p{4cm}p{10cm}}
\toprule
\textbf{字段} & \textbf{说明} \\
\midrule
\endhead
\texttt{retrieval\_source} & 证据来源于 BM25算法、vector 或两者。 \\
\texttt{bm25\_rank} & BM25算法 排名。 \\
\texttt{vector\_rank} & 向量召回排名。 \\
\texttt{bm25\_score} & BM25算法 分数。 \\
\texttt{vector\_score} & 向量相似度分数。 \\
\texttt{hybrid\_rank} & 融合后排名。 \\
\texttt{vector\_backend} & 向量后端类型。 \\
\texttt{field\_match\_score} & 字段级重排分数，用于衡量证据块是否真正命中当前字段语义。 \\

\end{manualtable}

\section{大模型结构化抽取技术详解}

\subsection{字段抽取流程}

结构化抽取逻辑位于 \texttt{extractor.py}。该模块将 schema、RAG chunks、字段级证据和模型调用串联起来，输出最终的 JSON 和 CSV。

\manualfigure{llm_structured_extraction_flow(2).pdf}{大模型结构化抽取流程图}

\begin{lstlisting}
加载 60 字段 schema
        |
构建 RAG chunks
        |
按字段召回候选证据
        |
按批次调用 LLM
        |
解析 JSON 返回结果
        |
目标年份表格对齐
        |
质量校验
        |
写出 JSON / CSV
\end{lstlisting}

\subsection{Prompt 约束规则}

Prompt 构造逻辑位于 \texttt{llm\_client.py}。系统将字段定义和候选证据传给模型，并明确要求模型输出固定 JSON 结构。主要约束包括：

\begin{itemize}
  \item 每个字段必须返回一条结果。
  \item \texttt{matched=false} 表示未披露或证据不足。
  \item 定量字段优先抽取 \texttt{value}、\texttt{unit}、\texttt{year}。
  \item 定性字段给出 \texttt{summary}。
  \item \texttt{value\_type=structure} 的字段必须返回完整分布摘要，不应返回单一数值。
  \item \texttt{evidence} 必须是证据中的短句。
  \item \texttt{confidence} 取值为 0 到 1。
  \item 优先抽取目标年份对应的数据。
\end{itemize}

\subsection{目标年份控制与表格对齐}

当前版本在 \texttt{extractor.py} 中新增目标年份表格对齐逻辑，核心函数为 \texttt{\_align\_result\_to\_target\_year()}。该函数用于修正多年份表格中的误抽问题。

ESG 报告中常见如下多年份表格：

\begin{center}
\begin{tabular}{lccc}
\toprule
指标 & 2020 & 2021 & 2022 \\
\midrule
年度培训总时长（小时） & 35000 & 36500 & 38700 \\
\bottomrule
\end{tabular}
\end{center}

如果目标年份是 2022，模型可能因为证据行换行或 PDF 文本顺序问题抽到 36500。系统会在候选证据中重新寻找目标字段所在行和年份表头，并根据目标年份位置取出对应数值，最终将 value 修正为 38700。

该机制支持以下情况：

\begin{itemize}
  \item 年份横向排列的表格。
  \item 年份表头被 PDF 提取为多行的情况。
  \item PDF 文本顺序不完全符合年份顺序的情况。
  \item 表格中同一证据块包含多个字段和多组数字的情况。
  \item LLM 返回 \texttt{matched=false}，但候选证据中存在可确定年份和值的字段表格行。
\end{itemize}

修正后，系统会将 \texttt{reason} 标记为 \texttt{year\_aligned\_from\_table}，便于后续检查。

如果 LLM 因证据片段不完整而返回未抽取，但后处理在候选证据中找到“年份表头 + 字段行 + 单位 + 多年数值”的确定性结构，系统会将结果从 \texttt{matched=false} 修正为 \texttt{matched=true}，并在 \texttt{reason} 中标记 \texttt{deterministic\_year\_table\_match}。例如绩效表中出现“2021 年、2022 年、2023 年”和“总用水量 吨 73,546,206 70,439,637 69,113,761”时，目标年份为 2023 的结果会被确定性补为 69,113,761 吨。

\section{结果校验与人工复核技术详解}

\subsection{结果校验规则}

质量校验逻辑位于 \texttt{quality.py}。该模块对 LLM 返回结果进行二次处理，补充标准化值、单位警告、年份警告、证据评分和质量提示。

\begin{manualtable}{p{5cm}p{9cm}}
\toprule
\textbf{校验项} & \textbf{说明} \\
\midrule
\endhead
年份校验 & 判断字段年份是否与目标报告年份一致。 \\
单位校验 & 判断单位是否缺失或是否与字段期望单位不符。 \\
证据评分 & 判断证据文本是否足以支撑字段结果。 \\
字段语义检查 & 判断证据是否命中字段名、别名或必需语义词，避免只因 evidence 出现在某行就相信该行。 \\
目标年份证据检查 & 如果定量字段证据中不包含目标年份，则标记 \texttt{target\_year\_not\_in\_evidence}。 \\
多数字歧义检查 & 如果证据中存在多个数字但没有目标年份，则标记 \makecell[l]{\texttt{ambiguous\_multi\_number}\\\texttt{\_evidence\_without}\\\texttt{\_target\_year}}。 \\
弱证据检查 & 证据评分低于阈值时标记 \texttt{weak\_evidence}。 \\
\bottomrule
\end{manualtable}

\subsection{弱证据降置信方法}

当前版本对多数字但缺少目标年份的证据进行了更严格处理。若一个定量字段已经匹配成功，但证据中出现多个数字且没有目标年份，系统会认为该结果存在歧义，并将置信度限制到不高于 0.35，同时将证据评分限制到较低区间，必要时将结果重新置为 \texttt{matched=false}。

该机制主要用于处理如下情况：

\begin{itemize}
  \item 多年份表格中只截取了数值行，没有截取年份行。
  \item 证据中同时出现多个年份或多个口径，但模型只返回一个数值。
  \item 证据无法明确说明当前值对应目标年份。
\end{itemize}

\subsection{置信度校准方法}

LLM 返回的 \texttt{confidence} 不直接作为最终置信度。质量校验会根据证据质量重新校准：如果字段名或别名、数值、单位和目标年份关系清楚，且没有严重质量警告，系统会将低估的置信度提升到与证据评分相匹配的水平；如果证据存在年份不明、单位异常、字段语义不匹配或多数字歧义，则会下调置信度。

该机制用于解决“数字正确但置信度只有 35\%”的问题。例如证据为“员工总人数：8,401 人”时，虽然证据句本身不重复出现目标年份，但它是单一数值证据，且字段语义、数值和单位都明确，系统会将置信度校准到较高区间；而“员工培训总时长 小时 36,500 38,700 39,600”这类多数字证据若没有年份表头，则仍会被视为低置信。

\subsection{复核优先级计算}

复核优先级计算逻辑位于 \texttt{api.py} 的 \texttt{\_review\_priority()}。系统会根据字段风险计算 0 到 100 的优先级。影响因素包括：

\begin{itemize}
  \item 字段未命中。
  \item 置信度较低。
  \item 缺少证据。
  \item 缺少来源页码。
  \item 证据质量评分较低。
  \item 年份异常。
  \item 单位异常。
  \item 人工已编辑但仍需确认。
\end{itemize}

\subsection{异常输入验证}

系统对以下异常输入进行处理：

\begin{itemize}
  \item 非完整 ESG 报告。
  \item 鉴证声明或审验报告。
  \item 摘要文件。

\subsection{抽取质量评估}

抽取质量评估主要关注：

\begin{itemize}
  \item 字段命中率。
  \item value 准确率。
  \item evidence 可用率。
  \item Top-K 证据召回成功率。
  \item 目标年份对齐准确性。
  \item 结构型字段完整性。
  \item 低置信结果人工复核命中率。
  \item 平均处理时间。
  \item MinerU 页面调用比例。
\end{itemize}

为了判断系统是否可以稳定用于报告分析，建议构建一个小规模人工评估集。评估集可先选择 5 到 10 份不同行业、不同版式的 A 股 ESG 报告，对 60 个字段进行人工标注或重点字段标注。每份报告至少记录字段是否披露、正确值、单位、年份、证据页和证据文本。系统输出后，再按字段统计命中率、值准确率、证据准确率和人工复核工作量。若定量核心字段的值准确率和证据准确率达到预设阈值，且低置信结果主要集中在报告未披露或证据确实模糊的字段，则可以认为当前架构基本稳定。

\subsection{召回模式评估}

系统支持比较以下召回模式：

\begin{itemize}
  \item simple：BM25算法 召回。
  \item hybrid + embedding：BM25算法 与 embedding 向量召回融合。
  \item local fallback：embedding 不可用时的本地向量兜底。
\end{itemize}

当前正式配置使用 \texttt{hybrid + embedding}，并叠加字段级重排和字段精确候选池。评估时可人工检查每个字段召回的 Top-K 证据是否真正支持抽取结果，并记录 BM25算法、embedding、RRF 和字段重排各自带来的改进。若某类字段长期召回失败，再考虑引入向量数据库或专门的表格结构化索引。

\section{总结与注意事项}

本文档围绕“智析万卷：面向 ESG 报告的自适应布局分析与要素提取”的实际实现流程，说明了系统从报告上传、页面筛选、选择性 MinerU 解析、RAG 文本块构建、字段级证据召回、大模型结构化抽取，到结果校验、人工复核、数据库存储和前端可视化的完整链路。系统通过规则筛选、版式解析、BM25算法、embedding、RRF 融合排序和字段级重排共同定位证据，并通过目标年份对齐、结构型字段约束和质量校验提高抽取结果的可复核性。

使用系统时需要注意三点。第一，字段结果应始终和证据文本、来源页码一起查看，不能只看抽取值本身；第二，低置信度、年份异常、单位异常和证据不足的结果应优先人工复核；第三，报告版式、字段命名和披露口径在不同企业之间差异较大，因此单份报告的运行结果不能代表整体效果，正式使用时应结合多份报告的复核记录判断系统表现。系统保留 JSON、CSV、数据库记录和前端复核状态，便于后续追溯每个字段的来源和处理过程。
